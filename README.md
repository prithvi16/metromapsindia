# MetroMaps India

An interactive atlas of rail in India — metro, suburban rail, monorail, light
rail, regional rapid rail, high-speed (bullet train), trams, funiculars and water
metros. Metro, light-rail and bullet-train lines come from OpenStreetMap;
suburban networks are imported from the India Rail Info atlas and drawn as one
uniform teal line.

- **Home** — every city in the index, with a generated SVG sketch and headline
  stats. Mapped totals and official Wikipedia figures are labelled separately.
- **City pages** — the full network on an OpenFreeMap Positron basemap, with
  layer filters for mode and construction status. Neighbouring cities stay on
  the map, so zooming out of Delhi reveals Noida and Gurugram.
- **Search (⌘K)** — jump to any city, line or station from a compact index.
- **About** — history, mode glossary and data provenance.

## Stack

| Piece    | Choice                                                                             |
| -------- | ---------------------------------------------------------------------------------- |
| Basemap  | [OpenFreeMap](https://openfreemap.org) Positron — vector tiles, no API key         |
| Renderer | MapLibre GL JS 5                                                                   |
| App      | React 19 + TypeScript + Vite 8, `react-router-dom`                                 |
| Data     | OpenStreetMap via Overpass + India Rail Info atlas, pre-built into per-city shards |
| Schema   | Zod, shared by the app and the pipeline (`shared/schema.ts`)                       |
| Server   | Express static server with SPA fallback                                            |
| Tooling  | Biome, Vitest, GitHub Actions                                                      |

## Getting started

```bash
npm install
npm run dev          # http://localhost:5173
npm run check        # typecheck + lint + data validation + tests
```

Node 22 is pinned in `.nvmrc`; `package.json` requires Node 20 or newer.

## How the map is built

Each city's lines are a GeoJSON source over the basemap — never baked into
tiles — so stations stay at exact coordinates and every line can be styled and
filtered independently.

Two visual channels keep nine modes readable at once:

- **Dash pattern = status** — solid operational, dashed under construction,
  dotted planned.
- **Width, casing and overlay = mode** — RRTS is widest with a white centre
  stripe, metro next, monorail and light rail get segmented white overlays, tram
  and funicular are thin and dotted.

The legend exposes mode chips, status chips and per-line eye toggles. Filters,
map position and a selected line are shareable through the URL.

### Shards and neighbours

A city page loads `shards/<slug>.json` plus the `neighbours` listed in
`index.json`. Neighbours are computed at build time from bounding-box proximity,
so Delhi loads Gurugram/Noida/Meerut and Mumbai loads Navi Mumbai plus the HSR
corridor. Loading the whole country on every page is deliberately avoided;
search uses the compact `search.json`.

Each city has generated `bounds` (a tight box around its drawn network) and a
`minZoom`. The map allows zooming out to a national view (`minZoom: 4.6`,
`maxBounds` set to India).

## The data pipeline

```bash
npm run data:refresh
```

1. **Fetch** — one Overpass query per city, cached with a query-hash sidecar so
   stale results are refetched automatically. Failures exit non-zero.
2. **Assign** — relations are matched to a city by `network` patterns, with a
   proximity fallback.
3. **Normalise** — ways are stitched, duplicate directions collapsed, stop
   positions canonicalised into stations, termini named from `from`/`to`.
4. **Curate** — `scripts/curation/<slug>.json` applies sourced status, station,
   added-line and drop fixes.
5. **Suburban import** — `scripts/suburban/<slug>.json` replaces OSM suburban
   lines with IRI corridors.
6. **Build** — geometry simplified (~5 m), stations clustered, previews
   generated, each shard validated with Zod, then `index.json` and `search.json`
   are rebuilt.
7. **High-speed corridor** — the Mumbai–Ahmedabad MAHSR is fetched from OSM
   relation 8304354 and pinned to its northbound way chain.

The build has guards against the obvious failure modes: no cache, a missing
requested city, a large coverage drop, and unresolved curation/suburban
warnings. See `docs/data-pipeline.md` for the full list.

### Cleaning up the data

```bash
npm run data:gaps                       # all cities
npm run data:gaps -- --city=mumbai      # one city
npm run data:geocode -- --city=mumbai --names="DN Nagar,ESIC Nagar"
```

Fixes live in `scripts/curation/<slug>.json`. See `docs/curation.md`.

The **transit-curator** subagent (`.opencode/agents/transit-curator.md`)
automates the research loop: read the gap report, open operator documents,
geocode names, write the patch, rebuild and re-check. It can only edit
`scripts/curation/`.

The **iri-suburban** subagent (`.opencode/agents/iri-suburban.md`) imports a
city's suburban network from the India Rail Info atlas and writes
`scripts/suburban/<slug>.json`.

### Coverage

OSM completeness varies. Cities with no usable relations are marked
`coverage: "none"` and appear as "Coming soon" cards; cities with fewer mapped
stations than ~60% of the official count are marked `partial`.

`counts.*` describe what is actually drawn (including IRI suburban);
`stats.*` stay the official Wikipedia figures. The index also lists four
announced systems — Surat, Bhubaneswar, Visakhapatnam and Coimbatore — as
coming-soon cards.

Figures come from Wikipedia's
["Urban rail transit in India"](https://en.wikipedia.org/wiki/Urban_rail_transit_in_India)
(CC BY-SA 4.0), as of October 2026.

## Deploying

`dist/` is fully static:

- **Vercel / Netlify / Cloudflare Pages:** build `npm run build`, output `dist`.
  `public/_redirects` is copied into the build and supplies the SPA fallback on
  Netlify and Cloudflare Pages. Vercel ignores `_redirects`; add an equivalent
  rewrite there if you deploy on Vercel.
- **Render / Railway / Fly.io / a VPS:** `npm install && npm run build && npm start`
  — Express reads `PORT` and serves `dist/` with an SPA fallback.

The build regenerates `sitemap.xml` and `robots.txt` from the city index. Set
`SITE_URL` when deploying on a different domain so those files use the right
origin; canonical and social metadata follow the page origin at runtime. No
tile keys are required.

For crawlers that do not execute JavaScript, the build also writes
`dist/about.html` and `dist/city/<slug>.html` with route-specific metadata.
`_redirects` points the clean URLs at those shells before falling back to the
SPA; the Express server does the same locally.
